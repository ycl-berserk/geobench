## D1 —— 实现栈（已定）

**结论。** 内核用 **Python 3.11+ / SymPy**；前端用浏览器技术栈（TypeScript + SVG 画布）；**Pyodide 可选**（浏览器内跑同一份内核）；MCP 服务端原生 Python（stdio），与前端共用同一份内核库。

### 为什么不需要 Rust / C++

被问到的核心问题是速度。逐条拆开：

- **端到端耗时的瓶颈不在内核。** 一次"出题"的实际链路是「Agent 思考 + 调工具 + 渲染」，其中 Agent 往返是**秒级**，内核计算是**毫秒~秒级**。内核快 100 倍，用户完全感知不到。
- **内核真正的瓶颈是符号表达式的复杂度，不是吞吐。** 化简一个含根号的判定表达式可能几十毫秒到数秒，这是 SymPy 的表达规模问题，**换语言解决不了**（Rust 也只是快一点）。能解决它的只有架构：
  - **符号证明每个构造族只做一次**（恒等式与自由点取值无关）；
  - **数值采样做很多次**（采样是廉价的数值运算，Python + numpy 完全够）。
  这条分界线是整个内核设计的核心，见 spec §6.1 的 `proved` / `supported` 之分。
- **引入第二语言的代价大于收益。** 一个语言意味着：两套工具链、两套测试、两套构建、AI 要同时遵守两套风格规范。对"实现尽量交给 AI"的单人项目来说，**少一门语言是特性，不是妥协**。

### 什么时候才需要换

明确写下来，避免将来凭感觉引入：

1. 精确算术核心（有理数 + 代数数域）需要跑到**百万级采样**量级；
2. v2 的 3D（用 OpenCascade，不自研）；
3. 渲染需要 GPU（v2 的 WebGPU 渲染）。

届时按"先测量、再优化"的规矩走：先出预测卡（假设 / 预期数值 / 判定阈值），再对照基线，**不接受只报一个漂亮倍数**。

### 关于 Tauri

**结论：v1 不用，记为 v2 备选。**

- Tauri 壳本身只有 ~5–15MB，但**只要内核是 Python，整体体积就由 Python + SymPy 决定**（venv 装完 80–150MB，打包后 40–80MB）。**Tauri 在这个架构下省不了体积**，却要额外背上：Rust 工具链、Rust↔Python 进程桥接、Windows 构建与签名负担，以及 AI 实现时的第三套规范。
- 若将来确实需要桌面壳，正确形态是**纯壳 + Python sidecar**：Rust 只做窗口、文件对话框、托盘与 IPC，**不碰几何逻辑**，内核仍是独立的 Python 进程。

### 体积账（"软件要小"的正确解法）

| 形态 | 首次下载 | 安装 | 离线 |
|---|---|---|---|
| 浏览器（Pyodide 跑内核） | ~10–20MB（含 wasm runtime） | 无 | 首次加载后可离线 |
| 本地 MCP | Python + sympy（已有 Python 者仅 +~30MB） | `pipx`/`uvx` 一条命令 | 完全离线 |

已核实：**Pyodide 内置包清单包含 sympy 1.14.0**（pyodide.org 内置包列表），因此"浏览器内精确符号几何"是现成可行路径，不是设想。

## D2 —— 精确算术实现（默认采用）

**结论。** 所有几何量用 SymPy 表达式，统一封装在 `Field` 协议（`add`/`sub`/`mul`/`div`/`sqrt`/`simplify_to_zero`/`to_float`）之后；内核中禁止浮点字面量，由 lint + AST 测试拦截。

**理由。** "这条关系成立"必须意味着**恒等**而不是"数值接近"。基于容差的内核无法区分 `proved` 与 `supported`，那整个项目的立论就没了。

**备选。** 自研"有理数 + 二次扩域"域：数值更快，但 `simplify_to_zero` 恰恰是符号正确性所在，不该重造。

**待观察。** 长构造链上的表达式膨胀。届时可加"仅有理数快路径"，但必须在 `Field` 协议内实现，不影响算子层。

## D4 —— MCP 工具契约（默认采用）

**结论。** spec §11.1 的十个工具 + §11.2 的资源；响应纯 JSON；错误可执行；**内核不含任何模型**。

**理由。** 工具契约就是产品面向 Agent 的接口，也是别人将来基于它做二次开发的东西。同时它倒逼内核以"对规划者有意义"的粒度暴露能力，而不是以"对 GUI 有意义"的粒度。

**备选。** 单个 `geo_do`（自由文本指令）：接口面小，但不可审计、不可测。HTTP API + 独立 MCP 包装：两套契约要同步。

**推论（重要）。** 因为内核不含模型，所以"自然语言 → DSL"这步由**客户端或外部 Agent** 完成；内核只提供 `geo_apply_dsl`（确定性解析）。这与 D7 的双通道设计一致。

## D6 —— 竞赛图规范（已定，待域主复核）

**结论。** 以 **TikZ 的通行约定**为基准 —— 竞赛圈制图的事实标准（TikZ 默认线宽 0.4pt、点 `circle(1.5pt)`、衬线标注），再叠加中国奥赛卷面的几条house rule：

| 属性 | 取值 | 依据 |
|---|---|---|
| 图形线宽 | 0.4 pt | TikZ 默认 |
| 辅助线 | 虚线（dasharray 3 2）、线宽 0.25 pt | 竞赛卷惯例：辅助线不计入主线 |
| 自由点 | 实心黑圆，半径 1.5 pt | TikZ `circle(1.5pt)` |
| 派生点 | 实心黑圆，半径 1.5 pt | 同上；派生点不另作区分 |
| 标注字体 | Times / STIX Two Text 衬线 | TikZ 默认数学字体族 |
| 标注字号 | 10 pt | 12 pt 文档下的 `\small` |
| 标注斜体 | 变量用斜体 | 数学排版惯例 |
| 标注位置 | 沿"图形质心 → 该点"方向外移，不压线 | 由渲染器自动计算 |
| 保留标号 | `O` 外心、`I` 内心、`H` 垂心、`G` 重心、`D E F` 垂足、`P Q R…` 自由点、`M N` 中点、`X Y` 交点 | 竞赛卷惯例 |
| 记号 | 圆 `⊙O`、线段 `AB` | 中文卷面惯例 |
| 图注 | **不画进图内**（"如图"属于题面） | 中文卷面惯例 |
| 三角形边 | 画**线段**（不是无限直线） | 卷面画的是边 |

**为什么这样定。** 这不是拍脑袋：TikZ 约定之所以是事实标准，是因为大部分竞赛题图就是 TikZ 画的，照抄它等于与现存卷面一致；而"辅助线虚线、图注在题面、边画成线段"这三条是中文卷面特有的，海外工具普遍做不对 —— 这三条恰好是差异化所在。

**待域主复核的点。** 标注字号的实际观感（10 pt 在 640px 的 SVG 里偏小）、辅助虚线的疏密、以及派生点是否要改成空心以区分自由点。这三条影响观感，不影响正确性，可以等第一批真图出来再定。

**为什么仍然重要。** 这是海外通用工具复制不了的护城河，也是 LLM 每次都会猜错的部分，必须写死而不是描述。

## D7 —— 交互范式（已定）

**结论。** **双通道**，汇入同一个构造图：

1. **手绘/交互通道**：直接拖点、点选工具 → 构造图。用于微调构型、试算、探索。
2. **text2graph 通道**：自然语言 →（AI 翻译或人工）→ **中文几何 DSL** → 构造图。用于从零起题、把题面翻译成图、Agent 批量出题。

两条通道之后的验证、退化检测、渲染、出题**完全一致**。

**关于"能不能用固定算法解决"**：能，而且必须这样分层。

- **DSL → 构造图：确定性。** 递归下降解析器，毫秒级、离线、零 API 成本、逐条可单测。
- **自然语言 → DSL：模型。** 但产物**必须过解析器校验**；解析失败时错误带精确行列，供 Agent 重试（与 `geogebra-mcp` 的错误驱动循环同构）。

**为什么不是纯手绘、也不是纯对话**：纯手绘慢（构造一题图要几十次点击）；纯对话不可信（模型会"看起来对"地错）。DSL 恰好是中间那个**既能被模型可靠产出、又能被确定性校验**的表示。

**备选。** 表单优先：精确但慢，压制探索。画布优先 + AI 侧栏：等于"GeoGebra + 聊天框"，不推荐。

## D11 —— 坐标表示：符号 + 摆放（已定）

**结论。** 自由点同时携带两套坐标：`coords` 是**符号**（`x_A`/`y_A`），`placement` 是**数值**（`("0","0")`）。派生节点由算子算出符号表达式，摆放则是同一表达式代入自由点数值后的结果。

**为什么这是必须的。** 最初实现里自由点只有数值坐标，结果"三点共线"永远只能是"这张图上共线"——**无法区分定理与巧合**。而竞赛命题的核心恰恰是"对任意摆放都成立"。判定器要问这个问题，自由点就必须是符号。

**代价。** 表达式规模暴涨（判定四点共圆的行列式到几千项），引出 D13。

**证据。** 改成符号后，同一个"两垂足与两顶点共圆"的断言从"这一张图成立"变成"恒等成立"，这才是可用的命题结论。

## D12 —— 判定作用域：identity 与 instance（已定）

**结论。** 判定有两个作用域：`identity`（对任意摆放成立）与 `instance`（当前这张图成立）。四个结论（`proved`/`refuted`/`supported`/`undecided`）在两个作用域下各自有明确含义。

**为什么。** 早期只有一个作用域，结果出现了两个荒唐现象：

- 断言"三个自由点共线"被判成 `proved`——因为它在**那一张**图上共线，但作为命题根本不成立；
- 断言"矩形四点共圆"判不出 `proved`——因为矩形不是恒等式，只是实例成立。

分成两个作用域后，两个断言分别落到 `refuted`（identity）与 `proved`（instance），语义就自洽了。

**用途划分。** 出题时用 `identity`（结论必须是定理）；审图、检验图形与题面是否自洽时用 `instance`。

## D13 —— 判定顺序与化简预算（已定）

**结论。** 判定**先采样、后符号**；符号化简**有预算**，超预算不硬撑，而是诚实降级为 `supported`。

**为什么先采样。** 反例即证明：找到一组摆放使表达式非零，关系就被**证伪**了，这一步只要几毫秒。而符号化简可能要几秒。让便宜的步骤先跑，常见情况（判一条假关系）就只付便宜的钱。实测判定器测试从 64 秒降到 16 秒。

**为什么要预算。** 自由点一多，表达式就长到几千项，sympy 的 `simplify` 会**永远算不完**（实测一个 4x4 行列式展开 17 秒、`cancel` 超过 300 秒不返回）。无预算 = 一个请求能挂住整个进程。

**归约策略（按代价从低到高）**：

1. `together` 取分子 → 按多项式判零（实测 0.1 秒 + 0.3 秒）；
2. `trigsimp` / `radsimp`；
3. 仅在表达式小于阈值时才 `simplify`；
4. 表达式超过预算（20000 ops）→ 直接返回"未能证明"。

**配套的两个实现细节**：

- **不用 `Matrix.det()`。** sympy 的通用行列式会展开；手写余子式展开保持因式分解，`together` 从 300 秒降到 0.1 秒。
- **比较两个表达式要能处理根式。** 内心的两种写法数值相等但 `simplify_to_zero` 判不出来（`QQ` 上的多项式判零对 `√146` 无效），所以对拍时额外走一次 `radsimp(simplify(...))`。

**底线。** 内核永远不会为了"看起来能用"而返回一个它没有证明的 `proved`。宁可说 `supported`，也不撒谎。

## D14 —— DSL 的"另一交点"语义：用代数捷径，不硬算根号（默认采用）

**结论。** 直线与圆的两个交点，按**二次公式中根号的正负**排序（0 号 = `+√`，1 号 = `−√`）；"另一交点"= 那个**不是已知点**的交点。求它时**不使用符号化简**，而用**代数捷径**。

### 为什么不直接比较两个根

最自然的写法是：把两个根分别与已知点做符号相等判断。但根里带 `√`，化简代价极高 —— 实测**挂住超过 10 分钟**。这是 D13 的同一件事在另一层的复现：**能代数地绕开的地方，就不要符号地硬算**。

### 代数捷径

把直线参数化为 `P(t) = P0 + t·v`，代入圆方程得到二次方程 `a·t² + b·t + c = 0`。已知点 A 在圆上时 `t = 0` 是它的一个根，于是：

- 另一个根 `t₂ = −b/a`（由韦达定理 `t₁ + t₂ = −b/a`，`t₁ = 0` 退化情形单独处理）；
- 更一般地，若已知点的参数是 `t_A`，则另一个根 `t₂ = −b/a − t_A`。

**全程不出现根号，而且不做除法。**

> **用"两根之和"，不用"两根之积"。** 积的形式是 `t₁·t₂ = c/a`，于是 `t₂ = (c/a)/t_A` —— **要除以已知根**。当已知点恰好落在参数化的基点上时 `t_A = 0`，答案就成了 `0/0`。这不是理论上的顾虑：DSL 演示里"垂足 D 在原点所在直线上"就真的返回了 `nan`（见 `tasks/T004-dsl-parser.failures.md` F11）。
>
> 和的形式 `t₂ = −b/a − t_A` **永远不除以根**，因此在基点情形下依然成立。

**基点也必须是典范的。** 参数化的起点取"直线上离原点最近的点"（`P0 = −c(a,b)/(a²+b²)`），方向取 `D = (b, −a)`。这样两个交点的编号只取决于直线的系数，不取决于"这条直线碰巧先与哪条坐标轴相交"——否则同一条直线换个写法，编号就变了。

### 由此引出的两条设计规则

1. **算子参数允许字面量。** 选择器（`0` / `1` / `other`）不是节点引用，是数据模型里的一等参数。此前数据模型隐含假设"参数都是节点引用"，这条被 T004 证伪并修正。
2. **对拍要比数学，不要比约定。** 内核给两个根排序用的约定（根号正负）是**任何独立实现都不会猜到的**——所以 `point.intersect_line_circle` 的对拍改用**集合比较**：对拍返回两个交点，内核选出的那个只要是其中之一就算通过。这比逐位置比较更严（它同时验证了"选出来的确实是交点"），而且不被约定污染。

**备选。** 让对拍复刻内核的根号符号约定：代价是对拍变成内核的影子，失去交叉验证的意义。**否决。**

**教训（已写进 `tasks/T004-dsl-parser.failures.md`）。** "慢"不会让测试变红，只会让 CI 卡住 —— 这类风险只能靠"先量再改"发现，不能靠"读代码觉得没问题"。

## D15 —— 工具响应的三态与类型化错误（已定）

**结论。** 每个 MCP 工具响应都带机器可读的 `status`，取值只有三个：

| status | 含义 | Agent 该做什么 |
|---|---|---|
| `ok` | 请求被理解且完整执行 | 继续 |
| `error` | 请求错了：未知 id、参数个数/类型不对、表达式不认识 | **改请求** |
| `degraded` | 请求没错，但几何算不出来：构型退化、图有结构问题 | 读原因，接受现实 |

错误另有**类型化**的内核异常：`ArgumentCountError` / `ArgumentTypeError` / `UnknownNodeError` / `DegenerateError` / `AmbiguousIntersectionError`，由 `tools/errors.py` 统一映射成结构化错误对象（`code`、`op`、`index`、`node_id`、`known_node_ids`）。

**为什么是三态而不是两种。** 最初只有"成功 / 失败"两种语义，于是三种性质完全不同的事情挤在一个 `errors` 数组里：参数写错（**我该改请求**）、构型退化（**我该接受现实**）、图被改坏（**内核有 bug**）。Agent 拿到一个错误却不知道该做什么，只能重试或者放弃。分成三态之后，每一种失败都自带一个明确的下一步。

**为什么错误要类型化。** "unknown node id 'Q'"这句话人读得懂，机器读不懂——它不知道该换成哪个 id。而"合法 id 列表"是**能自愈**的信息：agent 看到 `known_node_ids` 就能自己改对，不必再问一轮。**错误消息是给 agent 看的接口，不只是日志。**

**为什么 `degraded` 尤其重要。** 自由点是符号（决策 D11），所以"三点共线"在符号层面根本看不出来——行列式不是恒等于零，只是**这个摆放**下等于零。求值层因此单独检查摆放的有限性（`zoo` / `nan` / `oo` 即退化）。没有 `degraded` 这一态，内核只能假装成功，然后画出一个位于无穷远的点。

**底线。** 内核永远不会把一个没算出来的几何报成 `ok`。**宁可说"退化了，而且是因为这个"**，也不说"好了"。

## D16 —— 桌面外壳用 PySide6，单进程单语言（已定）

**结论。** 产品是一个**桌面软件**（双击即用的 exe），界面用 **PySide6（Qt Widgets）**，内核与界面在**同一个 Python 进程**里。D1/D10 里"浏览器前端（Pyodide 可选）"这一条**作废**；D1 的其余部分（Python 内核、SymPy、不引入 Rust/C++）与 D10 的"本地 MCP 通道"**不变**。

**为什么不是浏览器。** 域主明确要求"这是软件，不要网页"。而且从工程上看，浏览器方案要付出：第二个运行时、一个本地服务进程、端口与进程管理、两套代码风格 —— 而内核已经在 Python 里了。

**为什么不是 Electron / Tauri。**
- Electron：多一套 Node 工具链与 Electron 主进程/渲染进程；界面与内核之间要过 IPC。
- Tauri：要 Rust 工具链 —— D1 早就否掉了。
- 两者都让"AI 持续产出高质量代码"这件事的复杂度翻倍。

**为什么 PySide6 是三者里最好的。**
1. **零 IPC**：内核调用就是函数调用。这是"交互速度与 GeoGebra 看齐"的**前提**（D18）。
2. **一门语言**：内核、DSL、判定器、界面、测试、打包全在 Python 里。一套规范、一个测试运行器、一个打包器。
3. **Qt 在这个领域是验证过的**：GeoGebra Classic 5（真正在教室里用的那一版）就是 Java Swing —— 原生控件路线在这个领域是成立的。
4. **许可干净**：PySide6 是 LGPL，与 MIT 兼容。

**代价（已知并接受）。** 将来 AI 对话面板在 Qt 里比在 React 里麻烦。**推翻条件写在这里**：做到 v3 时若 Qt 的 UI 明显拖累产品（而不是"我更熟 React"），就换界面层 —— 界面层与内核层的边界从第一版就划清，换 UI 不动内核。

**备选。** ① 纯网页 + Pyodide：零安装，但 SymPy 在 wasm 里启动慢、包大，精确证明的等待会明显。② Electron + Python sidecar：UI 上限高，但多运行时 + IPC，与"少一门语言是特性"（D1）冲突。

## D17 —— 覆盖面 = GeoGebra 全部几何命令；DSL 改函数式（已定）

**结论。**
1. **覆盖面**：实现 GeoGebra 的**全部几何命令**（点、线、圆弧、多边形、变换、测量、判定、轨迹、圆锥曲线），**中文命令名与 GeoGebra 对齐**。不做 3D、CAS、函数绘图、统计、表格、脚本、滑块动画（那不是"几何内容"，也不在 D5 范围内）。
2. **DSL 语法**：从句子式（`D = BC 上 A 的垂足`）改为**函数式**，与 GeoGebra 中文命令名一致：`中点(A,B)`、`中垂线(A,B)`、`外接圆(A,B,C)`、`垂直(A,l)`、`交点(l,c)`、`共线(A,B,C)`。

**为什么改语法。**
- **老师不用学新东西**：他在 GeoGebra 里打的就是 `中点(A,B)`，中文名也一样。出题工具的采用成本，一半在"老师愿不愿意学"。
- **解析器大幅简化**：接近 S-表达式，健壮好写，模型也更容易生成对。
- **命令 ↔ 算子一一对应**：映射表直接对齐 GeoGebra 手册，缺口一目了然。

**为什么句子式废弃。** 句子式更"自然中文"，但它需要一套语法分析，而自然语言的理解本来就该交给 AI 那一层；DSL 层的职责是**确定性地**解析，不该抢自然语言的活。而且句子式与 GeoGebra 不兼容，等于让老师再学一遍。

**代价。** T004 的句子式解析器作废（约一天 AI 工时），`docs/dsl-spec.md` 重写。**值得**。

**为什么以 GeoGebra 为标尺而不是自己定。** 域主要求"速度看齐、借鉴就借鉴"。GeoGebra 的命令清单与手册给了每个命令的**确切语义**（参数、结果、退化情形），我们不用猜；而老师的肌肉记忆也在这儿。

**但有一条边界。** **GeoGebra 不作为对拍真值** —— 它也是数值内核（`GeoNumeric` 存 double），拿它当 oracle 等于用近似校验精确。对拍仍用 SymPy 的独立实现；GeoGebra 用作**语义参考**与**互操作目标**。

## D18 —— 性能：精确/数值双路径（已定）

**结论。** 求值拆成两条路：
- **精确路径**（SymPy）：只在"构造变了"时跑一次，结果按构造版本缓存；
- **数值路径**（float）：每次拖动都跑，微秒级，**不产生任何判定结论**。

数值路径用 `lambdify` 把**同一份符号表达式**编译成 float 函数 —— **算子只写一遍**。

**关键洞察。** 派生对象的符号表达式**不随自由点摆放变化**。中点的表达式永远是 `(x_A+x_B)/2`，拖动 A 不会改它一个字符。由此推出三条：

1. 拖动只走数值路径 → 永不快到卡；
2. 精确求值只在构造变化时做一次 → 判定前不必"现算一遍"；
3. **identity 结论与摆放无关**（这正是 D12 的定义）→ 拖动时 `proved` 仍是 `proved`。

**"和 GeoGebra 看齐"的可测定义**（`docs/plan.md` §7，CI 卡预算）：
拖动一帧 p99 ≤ 16ms · 新增构造 ≤ 50ms · 整图重绘 ≤ 8ms · 判定判假 ≤ 50ms · 判定判真常见 ≤ 2s、难例 ≤ 15s（异步 + 进度 + 缓存）· 冷启动 ≤ 2s。

**必须说清的边界。** **判定速度没有 GeoGebra 可比** —— GeoGebra 根本不判定。它慢的地方我们没法比，但**它快的每一处我们必须一样快**，否则用户会觉得我们更差。所以画板的两条反馈必须分开：**拖动只重绘（毫秒），松手才判定（可能慢）**。

**底线。** 数值路径**只用于显示**。`no_float` 门禁为它开一个**明确命名**的例外，并加一条测试断言"判定器不 import 数值路径"。宁可慢，也不让近似值出结论。

## D19 —— 借鉴 GeoGebra：三样东西（已定）

**结论。** 从 GeoGebra 拿三样：

1. **Construction Protocol** —— 构造以**有序步骤表**呈现（可导航、可编辑、拖动时标出重算了哪些步）。我们的构造图与依赖序已经具备，只是没在界面上露出来。
2. **undefined 语义** —— 退化时**把那个对象标成 undefined（变灰）**，而不是让整批失败。GeoGebra 拖点经过退化位置时，图形不崩，只是那个点没了。我们现在是"整批 `degraded`"，更粗。
3. **`.ggb` 兼容** —— 导入/导出 GeoGebra 的 XML。**价值很高**：老师已有大量课件，能直接打开是采用率的关键。

**不借鉴的。** GeoGebra 的**数值内核**。我们默认精确（D2），这是我们强的那一档（D12/D13/D15）。**不要为了像它而把自己降级。**

## D20 —— 一份原语列表，两个渲染后端（已定）

**结论。** 内核产出**一份原语列表**（点 / 线段 / 直线 / 圆 / 标注），`QPainter`（屏幕）与 `SVG`（导出）**两个后端吃同一份**。

**为什么。**
- **Qt 的 SVG 渲染慢**，不能每帧重解析 SVG —— 屏幕必须走 QPainter 直接画。
- 但**屏幕与导出必须一致**，否则老师看到的和卷面上印的不一样。
- 一份原语 + 两个后端 = 一致性由结构保证，且**有测试盯着**（两个后端产出的原语集合逐条相等）。

**它取代了什么。** 原来的"屏幕直接显示内核的 SVG"（所见即所导出，但慢）。现在的一致性靠**同一份原语**而不是**同一串字节** —— 同样强，但更快。

**备选。** ① 屏幕也用 SVG（Qt 渲染慢，否决）。② 只做屏幕不保证导出（否决：卷面是产品的终点）。③ Web 渲染器（若将来换 Electron，原语列表直接复用 SVG/Canvas 后端 —— 这也是 D16 那条边界划得有用的原因）。
