# AI 实现流程

**原则：模型写代码，人写规格并裁定真伪。**

本文不是风格指南，而是让项目的核心主张变得可信的机制——"几何软件可以在人的契约约束下由 AI Agent 生产"——它同时也是项目本身的**证明材料之一**。

---

## 1. 为什么是这个形态

几何内核的代码有一个罕见而好用的性质：**几乎每一行都可判定**。一个算子要么算出正确的点，要么没有；一个判定器要么证明关系成立，要么没有。这让"模型负责打字、机器负责裁判"的分工格外成立：

- 人写的**规格**比人写的**实现**更无歧义；
- AI 生成的实现**产出便宜、丢弃也便宜**；
- 真正贵的部分——判定什么是真的——恰好可以在内核里**确定性地**自动化。

于是人的稀缺注意力集中在：**范围、语义、品味（什么样的图算竞赛图）、以及规格没预料到的边界情况**。

## 2. 分工

| 人（域主）负责 | Agent 负责 |
|---|---|
| `spec.md`——语义、算子/判定器契约、结论含义 | 实现算子、判定器、工具与测试 |
| 范围决策（D5）、图规范数值（D6） | 属性化测试与反例测试组 |
| "什么算一道好竞赛题"的判断 | 与独立实现的对拍 |
| 接受或拒绝一个任务 | CI 配置、打包、文档草稿 |
| 最终的"这题到底成不成立" | 在任务约束内的重构 |

人**不**审查代码风格。lint 与类型检查是门禁，不是评审项。

## 3. 任务生命周期

```
 提案 ──▶ 已规格化 ──▶ 已实现 ──▶ 门禁通过 ──▶ 已接受 ──▶ 合并
   │         │            │           │           │
   │         │            │           │           └─ 人：结论语义、
   │         │            │           │              品味、边界情况
   │         │            │           └─ CI：lint · types · unit · oracle ·
   │         │            │              property · degeneracy · no-float ·
   │         │            │              contract
   │         │            └─ Agent 产出代码 + 测试
   │         └─ 任务文件里的验收标准是**可执行的命令**
   └─ 想法，来自人或来自 issue 列表
```

没有任务文件（验收标准是可执行命令）的任务，不进入"已实现"。

## 4. 任务粒度

一个任务 = 一个行为单元 + 它的测试 + 它的对拍。具体地，一个任务实现**一个算子**、**一个判定器**、**一个 MCP 工具**，或**一块基础设施**——不是"几何模块"。

- 目标规模：含测试 ≤ 300 行改动。超出就拆。
- **功能任务里不做顺手重构。** 重构单独立任务，这样失败可归因。
- 一个任务最多触碰内核的一层（层次顺序见 spec §14 的验收：模型 → 算子 → 判定器 → 求解 → 渲染 → 服务端）。

## 5. 门禁（全部在 CI，全部阻塞）

| 门禁 | 命令 | 保护什么 |
|---|---|---|
| lint | `ruff check .` | 风格、禁用模式、**内核中的浮点字面量** |
| types | `mypy src` | 契约漂移 |
| unit | `pytest tests/unit -q` | 行为 |
| unit/dsl | `pytest tests/unit/dsl -q` | DSL 解析与往返 |
| oracle | `pytest tests/oracle -q` | 算子对独立实现的正确性 |
| property | `pytest tests/property -q` | 随机输入下的恒等式级正确性 |
| degeneracy | `pytest tests/degeneracy -q` | 边界情形处理 |
| no-float | `pytest tests/no_float -q` | spec §4 的精确性不变式 |
| contract | `pytest tests/contract -q` | 公开 API 与 spec 一致 |
| integration | `pytest tests/integration -q` | **真的从外面进来**：真进程、真客户端、真协议 |

附加规则：

- 每个判定器必须有一条**正例**与一条**反例**测试。给不出反例的判定器不上线。
- 每个算子必须有 ≥ 20 组对拍构型，其中 ≥ 3 组退化；对拍框架会打印覆盖表，**没有对拍行的算子即 CI 失败**。
- `proved` 结论必须可复查：`geo_verify` 的响应要带归约后的表达式与所用假设。

## 6. 失败协议——真正重要的那一节

**每一次被拒的 Agent 产出都要留档，不许删除。** `tasks/<任务号>.failures.md` 累积记录：

```markdown
### F2 — 2026-11-08 · sympy 化简返回了非零余项
- **任务**：T004 point.foot
- **症状**：一个显然为直角的判定返回了 `undecided`。
- **根因**：Agent 假设 `simplify()` 会归一化三角恒等式；它不会。
- **修法**：改用 `trigsimp` + `simplify`，再 `cancel` 后与 `0` 比较。
- **本该拦住它的门禁**：对拍电池（缺了直角三角形这一组夹具）。
- **动作**：向 `tests/oracle/fixtures/right_triangle.json` 补入该夹具。
```

这份日志是 AI 辅助工程的**诚实证据**：它展示了什么坏了、为什么坏、以及事后收紧了哪道门禁。只有成功记录的仓库，对流程本身什么都证明不了。

## 7. Prompt 规则

模板在 [`../prompts/`](../prompts/)，模板里固化的规则：

1. **原文引用规格。** 给 Agent 的是 `spec.md` 的相关章节原文，不是转述。
2. **不许自造 API。** 必须沿用既有注册表/接口模式；新增公开 API 要先改规格。
3. **先写测试。** Agent 先写会失败的测试（判定器还要写反例），再写实现。
4. **禁止浮点。** 明确写出，因为这是 Agent 最常破坏的不变式。
5. **禁止静默近似。** 精确计算做不到时，抛类型化错误——绝不返回浮点数碰运气。
6. **歧义即错误，不得猜。** 交点序号、弧的选择、"那个"圆，都必须显式；规格没说就问，不许默认。
7. **只报告，不宣称。** 最终回复必须包含：改了哪些文件、跑了哪些命令及其真实输出、已知限制。

## 8. 度量流程本身

流程与代码一样被度量，因为它的质量是项目主张的一部分：

- **接受率**：按任务类型（算子 / 判定器 / 工具 / 基础设施）分别统计。
- **到达绿色的迭代次数**：中位数与 p90。
- **门禁命中直方图**：哪道门禁拒得最多（这直接告诉我们规格哪里写得不够）。
- **Agent 任务引入的回归数**。

这些数字在每个里程碑写回本文，原始数据放在 `evals/reports/`。

## 9. 工具链

内核通过 MCP 服务端（spec §11）暴露，任意 MCP 客户端均可驱动——人用它做交互，Agent 用它做批处理。**没有给 Agent 的特权路径：Agent 能调的，人也能调**，Agent 的每一步都记录在图形状态里，并可由题库文件复现。

## 10. 两处特别提醒

- **DSL 解析器（spec §9）是确定性代码**，不允许 Agent 用启发式"差不多能解析"的方式实现。解析失败必须精确报错；宁可少支持一种句式，也不能给出错误的几何。
- **AI 负责翻译，解析器负责拒绝。** text2graph 通道的可靠性来自这条分工，不来自模型更聪明。

## 11. 实践约定（Agent 侧）

这些不是审美偏好，是**踩过之后定下来的操作纪律**。

### 11.1 含中文的文件不要用 PowerShell 做批量文本改写

Windows PowerShell 的 `Get-Content` / `Set-Content` 在读写时会按当前代码页（简体中文机器上是 GBK）解释字节，**UTF-8 的中文被读成乱码再写回**，文件就此损坏。实测一次正则批量替换让 `dsl/parser.py` 出现 162 处语法错误，`⊥` / `∥` 等字符被彻底破坏（GBK 解码时字节丢失，不可逆）。

**规则：**

- 用编辑工具（逐处精确替换）改文件，**不用** `Set-Content` / `Out-File` 做批量替换；
- 需要脚本化改文件时，写一个 Python 脚本，用 `encoding="utf-8"` 显式读写；
- 改完含中文的文件后，**先跑一次 UTF-8 扫描**（读一遍全文，检查有无 `U+FFFD`），再跑测试。

**为什么单列一条。** 语法错误是"响亮的失败"，会被门禁立刻抓住；但**字符被静默替换**是"安静的失败"——如果那次改的是一个字符串常量里的字，门禁不会红，图却画错了。中文项目里这类风险必须靠纪律挡住。

### 11.2 中文词法器必须先试关键字，再试标识符

Python 的 `str.isalpha()` 对汉字返回 **True**。任何"以字母开头即标识符"的分支都会把 `点`、`断言` 切成名字。**汉字与 ASCII 必须走两条路径，且关键字匹配在前。**

### 11.3 先量再改

一个 4×4 行列式展开 17 秒、一个带根号的比较挂住 10 分钟——这些不是读代码能发现的。**改动前先跑一次基线并记下时间**，改动后再跑一次对比。

### 11.4 一个变量不要兼职两件事

解析器里曾用 `index` 同时充当"游标"和"是否找到关系词"的标志位，于是"找到关系词后 index 推到末尾"与"index 超界"这两个条件永远同时成立。**状态用独立变量表达**，不要用位置推断。

### 11.5 每道门禁都有盲区，记下来

- **`no_float` 只拦浮点*字面量***，拦不住 `float(x)` 这样的**调用**。T003 里就出现过一次：用 `float(text)` 去判断"这个参数是不是数字字面量"。门禁是绿的，规矩被破坏了。
  → **补法**：这类地方要靠**代码走查 + 契约测试**补，不能指望门禁。
- **`unit` 拦不住字符串里的错字**。语法错误是响亮的失败；字符串常量里的一个错字是安静的失败——门禁不会红，图却画错了。
  → **补法**：`tests/unit/test_encoding.py` 之外，**渲染结果要有肉眼可查的样例**（`examples/` 下的产物）。
- **门禁只覆盖已经写下来的规则**。规格没写的边界，测试再多也拦不住。

**原则：门禁是下限，不是上限。** 门禁能挡住"写错"，挡不住"想错"。所以每道门禁旁边都记着它的盲区，新任务开工时先看这张表。


## 12. 钥匙放在哪：一条优先级链，不是一个答案

每个 agent 工具都要回答同一个问题——**模型服务的钥匙放在哪**。
Claude Code、Cursor、Cline、Continue、Copilot CLI、OpenCode、Gemini CLI
都答了，而且答案惊人地一致：**不是单选，是一条优先级链**。

| 工具 | 钥匙的来源 |
|---|---|
| Claude Code | 环境变量 → 系统钥匙串 → `~/.claude/.credentials.json` |
| Cursor / Windsurf | 系统钥匙串 |
| Cline | VS Code 的 SecretStorage（加密） |
| Copilot CLI | 系统钥匙串；没有就退回明文文件（会问） |
| Continue | `~/.continue/config.json`（明文），支持 `${ENV_VAR}` 替换 |
| OpenCode | `~/.local/share/opencode/auth.json`（CLI 与桌面版共用） |
| Gemini CLI | 环境变量 / `~/.gemini/.env` |

共识是这条链：**环境变量 → 系统钥匙串 → 应用自己的设置**。

本项目照这个做，取 Claude Code 记录在案的那个顺序：**环境变量优先**。
理由不是安全，是**不打扰**：已经导出过密钥的用户不该被再问一遍。

### 12.1 规矩

1. **环境变量赢**（除非用户明说「用我保存的那个」）。已经导出的密钥不被悄悄覆盖。
2. **什么都没配置时，环境里已有的密钥会选中它对应的服务** —— 开箱即用。
3. **设置文件与密钥文件分开**。设置可以被复制给别人看，密钥不行。
   密钥文件里可以写 `${VAR}`——**说清楚钥匙在哪，而不含密钥本身**。
4. **界面必须说清楚钥匙会从哪来**。「不工作」不是一个答案，
   「去检查你的环境变量」对不懂环境变量的人也不是。找不到时要说**缺什么**。
5. **密钥永远不写进日志、不写进测试夹具、不进版本库**。
   测试用 `GEOBENCH_CONFIG_DIR` 指向临时目录，**不碰用户真实的设置目录**。

### 12.2 为什么这一节写在这里

这不是某个模块的实现细节，是**项目级的约定**：
以后加任何要密钥的东西（新的服务商、本地模型、MCP 服务器的鉴权），
都照这条链走，不要每次重新发明一套。

## 13. 作图 skill：模型怎么学会用这个软件

用户问的是「AI 直接接进来，它真的能画好吗」。**这件事只能测，不能猜。**

### 13.1 实测（真模型，6 道真实命题作图请求）

| 步骤 | 结果 |
|---|---|
| 旧提示词 | **0/6 出图** |
| 原因 | 模型写 `A(0,0)`，**漏了「点」字** |
| 解析器回话 | 「不认识的命令 'A'」—— **没说怎么改** ⇒ 重试照旧犯错 |
| 把「点」补回去 | **5/6 完美出图**，几何全对 |

**结论：模型的画图能力没问题，差的全在「契约」上。**
所以要补的不是「让模型更聪明」，是三样东西：**示范**、**能照着改的错误**、**有人验**。

### 13.2 skill 的三层（`prompts/`）

| 层 | 文件 | 为什么 |
|---|---|---|
| 规则 | `nl-to-dsl.md` | 九条硬规矩，短、点名 |
| **规范** | `figure-standards.md` | 命名 · 画什么 · **做不到的事** · 坐标要满足题面条件 |
| **范例** | `figure-examples.md` | **范例比规则管用**（实测） |
| 命令 | —— | **从命令表生成**，不会过时 |

规范里有一节叫「**做不到的事**」：**从圆内一点作切线**是做不出来的 ——
**说清楚做不到，比画一张假图强**。模型现在会写 `# 做不到：……`。

这一节是**评测集逼出来的**：第一版评测里，模型把「圆内一点 P」悄悄换成了
「圆上一点 P」—— 图是对的，但不是题目的图，而且一句话没说。现在
`must_not_relate` 专门抓这种**偷偷替换**。

（评测集也顺手把软件本身补了一块：原来从**圆外**一点作切线做不了，
模型一写就撞墙；T042 之后 `切线(P, c)` 对圆上、圆外都成立。）

### 13.3 自检闭环

```
模型写代码 → 解析器判（语法） → 内核判这张图（几何） → 有问题就把原因喂回模型重画
```

内核判的是两件事：**有没有算不出来的对象**（两条恒平行的线的交点）、
**断言在这张图上成不成立**。判定用**实例作用域**（毫秒级）；
「是不是定理」是老师按下按钮才跑的另一件事。

### 13.4 错误信息是教学通道

解析器说「自由点要写成「点 A(x, y)」」，模型下一次就不会再漏那个字；
说「不认识的命令 'A'」，模型就会再写一遍 `A(0,0)`。
**重试机制只在错误信息可操作时才有意义。**

### 13.5 度量

`evals/` 是评测集：每个用例有**期望**（题面点名的对象、断言、坐标条件、线段条数）。

- `scripts/eval_ai.py` —— 手动跑真模型（**不碰网络，不进 CI**）
- `tests/eval/` —— 假 provider 回放**录下来的真答案**，**AI 产出过 CI 门禁**

| | 通过 |
|---|---|
| 旧提示词 | **0/8** |
| 新 skill | **8/8**（每例一次就过） |

被拒的产出留档在 [`../tasks/T041.failures.md`](../tasks/T041.failures.md)，不许删除。
