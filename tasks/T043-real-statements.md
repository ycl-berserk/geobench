**负责人**：Agent
**规格**：[`docs/ai-workflow.md`](../docs/ai-workflow.md) §13

**涉及层**：服务端 · 应用 · DSL · 算子

## 问题

用户说：

> 现在 ai 还是没有办法根据我的自然语言进行绘图，这中间肯定是很困难的，
> 应该没有你想象的这么简单。我觉得你需要查阅一下类似的 ai 产品是怎么解决相关问题的。

**这话是对的，T041 的结论被我夸大了。** 那 9 道题是**我们自己写的**、措辞是我们定的、
每道只试一种说法，而且规范里还给了模型一张「稳坐标」表。
它测的是**契约**（模型学没学会我们的语言），**不是**「产品能不能接住任意题面」。

## 一、调研：同类产品实际怎么做（四个模式）

### ① 学术派：**形式化几何语言**

Inter-GPS、PGPS9K、GeoQA/UniGeo、GeoX（ICLR 2025）、GOLD（NAACL 2024）。

- **关键结论**：GeoX 报告「**形式语言比自然语言更有效**，Geometry3K 的 Completion +2.9%」。
- **两阶段分解**：Interpreter（把图/题面变成**符号化的形式文字**）→ Solver（在文字上推理）。
- **符号层与图元层分开**：GOLD 把「符号（哪些字母）」和「几何基元」**分别处理**。
- **评测集**：Geometry3K（3001 道）、UniGeo（**9543 道中国高中教材题**）、GeoQA（4998 道中国初中题）、
  PGPS9K、GeoEval（24912 道）。

> **对我们的意义**：我们的架构（模型 → DSL → 确定性内核）**就是**这一派，选对了。
> 缺的是：符号/图元分开、两阶段拆分、**用真实题库的分布做评测**。

### ② 商业图示派：**模型不画，引擎画**

Excalidraw 的 text-to-diagram 公开了原理：**prompt → Mermaid → 图**。
模型只产出**声明式规格**，坐标、连线、标签位置**全部由引擎负责**。
Miro / FigJam 同理。

> **对我们的意义**：**让模型编坐标是错的方向** —— 而且规范里那张「稳坐标」表
> 就是这个错误的拐杖（下面第三节有它怎么变成"制造错误"的实录）。
> 模型应该写**关系**，引擎解出坐标。

### ③ CAD 参数化约束求解（SolveSpace / CAD Sketcher）

未知量 = 坐标，方程 = 约束，数值牛顿法迭代；
状态分类成熟：**欠约束 / 完全约束 / 冗余（但一致）/ 不相容 / 不收敛**；
「**初始猜测决定选哪一个解**」。

> **对我们的意义**：这就是「锐角三角形、AB=AC、∠A=90°」该走的地方。
> 我们的 spec §8 早就规划了 `geo_solve`（约束求解与变体）—— **只是从来没建**。

### ④ 视觉闭环（Render-in-the-Loop ECCV'26 / IntroSVG CVPR'26 / TikZ 的"不完美验证"）

- 「现有范式是**开环的盲画**……我们把渲染结果喂回模型，让它**边看边画**」。
- Generator-Critic：起草 → 渲染 PNG → 批判（打分 + 可执行的修改建议）→ 改 → 再渲染。
- 「输出以视觉为主时，正确性**无法形式化**，只能靠**不完美验证器**」。

> **对我们的意义**：我们现在是**开环**的：模型写代码、内核查几何，**没有人看过那张图**。
> 而「像不像」恰恰是内核判不了、老师第一眼就看出来的东西。

### 顺带：我们的正面对手 GeoGebra 也不做「NL → 图」

GeoGebra Discovery 做的是**给定一张图 → 发现/证明定理**（Prove / ProveDetails /
Discover，301 道测试定理能证 255 道），不是「说一句话 → 出图」。
所以「一句话出图」这件事，**整个市场都还没做好**；市面上的答案是 ②（模型写规格、引擎画）。

## 二、评测集：22 道真实题面

`evals/statements.py`：每道题面带

- **题面**（老师会怎么打）；
- **条件**（长度、角度、垂直、平行、中点、共圆、相切……）—— 机器可查；
- **参考图**（手工写的正确构造）—— 它验证**检查函数本身没错**，
  也是「模型应该画成什么样」的标尺；
- **类型**（数值条件 / 关系构造 / 定理型 / 改述），报告按它分组。

`tests/eval/test_statements.py` 检查**参考图必须满足自己的条件** ——
检查函数错了，这道题就废了。（它当场抓出三个错：见第四节。）

CI 门禁（`tests/eval/test_eval_harness.py`）的规矩：
契约用例**必须仍然通过**；真实题面**必须仍然以同样的方式失败** ——
哪天有一道开始满足了，门禁会**报喜并要求重新录制基准**，
所以基线只能是有意移动的。

## 三、实测：21/22，以及三个发现

| 类型 | 通过 |
|---|---|
| 关系构造 | 6/6 |
| 定理型 | 8/8 |
| 改述 | 2/2 |
| **数值条件** | **5/6** |

### 发现一：那张「稳坐标」表**正在制造错误**

题面要「顶角 40° 的等腰三角形」，模型套用了表里的 `点 A(0,3) B(-2,0) C(2,0)` ——
**等腰是对了，顶角不是 40°**。图看着挺像，**其实不满足题面**，而且看不出错在哪。

改法（实测 19/22 → 20/22 → 21/22）：
**长度靠"摆"（整数长度直接摆坐标），关系靠"构造"（角度用旋转、比例用位似）**，
并明写「不要背坐标」。这比原来那张表**更短**，也更像老师教学生的方式。

### 发现二：**角平分线的参数顺序**从没在规范里写过

模型写 `角平分线(B, A, C)`（顶点写第一位），内核读成「∠BAC 的平分线」——
画出来的是**另一条**平分线，**而且不报错**。

查 GeoGebra 手册：「**Point B is apex**」—— 顶点是**第二个**参数。
**内核是对的，规范漏了。** 于是规范补上这一条（并点名它是"写反了不会报错"的那一类）。

### 发现三：两个 DSL 的洞

1. **同名重定义**：模型想分两步做同一个点（先旋转再位似），
   GeoGebra 允许（同名即替换），我们报「名字 'D' 已经用过」。
   → **唯一没过的那道题就是这个**。
2. **坐标只收有理数**：`C(2, 2*sqrt(3))` 写不出来。内核是精确的，
   `sqrt(3)` 本来就该支持 —— 这是**语法**的限制，不是精确性的限制。

### 还有一个：我的第一版题面里**有一道是矛盾的**

「∠A=90°、AC=4、BC=3」—— BC 是斜边，不能比直角边短。
**评测集的题面必须是对的**，否则测的是模型的想象力。
这是配「参考图」的另一个理由：参考图过不了，就说明题面或检查错了。

## 六、已知限制

- 题面是**我们自己写的** 22 道 —— 分布仍然是我们的，不是题库的。
- 只测了一个模型（DeepSeek）、一种问法、没有重试平均；单次运行有波动。
- 数值条件能过，多半因为**长度是整数**、能"摆"出来；
  需要真正计算的题目（无理数长度、非整数角度）**一道都没有**。
- 22 道题里的参考图**只有一份**（不是多解）——
  有些题面有多解（比如两条切线取哪条），参考图只是其中一种。
