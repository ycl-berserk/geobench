# T049 —— 大图不卡：精确算不动的时候，图照样能画

**状态**：已实现
**负责人**：Agent
**规格**：[`docs/spec.md`](../docs/spec.md) D18/D19
**依赖**：T034（导入撞出来的）
**涉及层**：内核 · 应用

## 问题

用户导入了一张真实的 GeoGebra 竞赛图（35 行 DSL）。**打开要 15 分钟以上** ✗ ——
不是画图慢（画图是 0.03 ms 一帧 ✗），是**精确求值没有上限**：

| DSL 行数 | 精确求值 |
|---|---|
| 14 | 0.8 s |
| 22 | 3.4 s |
| **26** | **26.9 s** |
| **31** | **> 90 s** |

用户的话：**"复杂图不该影响使用，GeoGebra 多复杂都很快。"** —— 他是对的。

## 两个洞，量出来的

1. **`evaluate_figure` 没有预算**：每个对象都埋头算，算完才轮到下一个。
2. **`zero_status` 的预算数错了量**：它挡"恒为零"的代数判定，但用的是 `count_ops < 20000`
   ✗ —— 而真正贵的是**建多项式**。实测：T040 那个行列式 **73 ops**（1 秒内判定 ✓），
   导入图那个 **8063 ops**（建多项式要几分钟 ✗）。**展开项数分不开它们**（都被算到上限值），
   **运算数分得开** ✓。

## 做法

### ① 精确层有预算，且**按运算数**算

- `evaluate_figure`：每个对象算完，`count_ops > 5000` 就**不留**这个表达式，
  标成"超出精确预算"；**依赖它的对象也跳过**（不是因为算不出来，是因为它的输入没有值）。
  预算校准：22 张真实竞赛图里最大的表达式是 **187 ops**（中位数 ~20）→ 5000 是 25 倍余量。
- `zero_status`：`count_ops > 2000` 就回答 **"不知道"**（`None`），不建多项式。

### ② 精确算不动的，**用数值直接算**

`evaluate_numeric_direct`：**同一份算子代码，喂进去的是数**，不是符号 ——
`NumericOpContext` 把 `point/line/circle/segment/polygon` 换成读数值载荷。
于是：

- **图照样画**（50 个图元，3 ms）；
- **照样能拖**（数值路径本来就是毫秒级）；
- **判定拒绝回答**，并说清原因（不是"不成立"，是"这张图超出精确预算"）。

**关键测试**：数值直算的结果必须和**编译出来的数值路径**逐个相等（1e-9）——
否则"降级"就等于画了另一张图。

### ③ 应用侧

- `controller.evaluate()`：精确 → 若"太大" → 数值直算 → 图画出来；
- 状态栏：**"这张图画得出来，也可以拖；但它太大，精确求值超出预算，判定不回答（原因）"**；
- 判定：直接 `undecided` + 原因（**不在小数上做判定**，D18）。

## 实测

| | 之前 | 之后 |
|---|---|---|
| 打开那张 35 行的图 | **> 15 min** | **3.1 s** |
| 画出来（50 个图元） | —— | **3 ms** |
| 判定 | 卡死 | 拒绝回答，并说清为什么 |

## 已知限制

- **降级的图不能判定**（这是设计，不是缺陷）：精确表达式不存在，就不在小数上做判定。
- 预算按**运算数**，不按"图形对象数" —— 一个对象可以很便宜也可以很贵。
- 数值模式下**不查退化条件**（`must_be_nonzero` 等）：屏幕上可能出现一瞬间碰巧重合的摆放，
  但不会被画错成"确定的图"（非有限值不画）。
- **弧/扇形/测量**的数值直算没有专门测试（它们走同一条算子路径）。

---

# 续：3 秒也不要 —— 打开就出图

**用户**：「**3秒也不要，具体实现你直接来做吧**」。

上一节把打开压到 3.1 秒，但那 3 秒仍然是**在等精确层**：`evaluate()` 先算完表达式，
才开始画。顺序反过来就好了 —— **先画，再判**。

## 做法

| 步骤 | 在哪 | 做什么 |
|---|---|---|
| ① 立刻画 | `controller.evaluate()` | 只跑 `evaluate_numeric_direct`（同一份算子喂数字），`runtime["exact"]` 标 `pending` |
| ② 后台判 | `Window._refresh_exact()` | 在**另一个线程**、对**图的副本**跑精确求值（复用判定那套机制），完成后 `absorb_exact` |
| ③ 吸收后判定 | `Window._on_exact()` | 精确到达后才请求判定；超预算就说明原因 |
| ④ 同步入口 | `controller.judge()` / `evaluate_exact()` | `pending` 时先补精确（测试和"现在就告诉我"用） |

**最多同时一个 worker**：编辑时只把请求号 +1；正在跑的 worker 完成时发现自己的答案过期，
就对**现在的图**重跑。否则敲十下构造 = 十个精确求值同时抢 CPU。

**数值直算也要守 D19**：现在会标 `undefined` 并给原因（和精确路径同一种语义），
并且分得清两件事：

- **构造本身是错的**（`直线(A, A)`）→ 输入都有值、算子仍拒绝 → **原子拒绝、回滚**；
- **这个位置退化**（三点共线、两线平行）→ `DegenerateError` → 对象暂时没值，**图继续活着**。

## 实测（老师那张 35 行图）

| | 上一版 | 现在 |
|---|---|---|
| 打开（图上屏） | 3.1 s | **5.5 ms** |
| 图元 | 50 | **50** |
| 拖动一帧 | 3 ms | **7 ms** |
| 精确层 | 挡在打开路径上 | **4.9 s，后台算完**（结论：超出预算） |
| 判定 | 等 3 秒后拒绝 | 一到就拒绝并说明原因 |

## 已知限制

- 精确层在后台仍会**每次编辑重算一遍**（最多一个线程）。大图上这是一次 5 秒的后台开销，
  不挡手；要彻底省掉，需要"构造只增不减时跳过重算"的缓存策略，等真的碍事再做。
- 后台精确层到达之前，**符号恒退化的对象**（两条恒平行直线的交点）可能被数值层短暂画在
  远处；到达后会被标成"没有值"并说明原因。这是"先出图"的代价，且只持续几秒。
