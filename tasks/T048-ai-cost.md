# T048 —— AI 通道的成本：先量，再砍

**状态**：已量 + 第一批优化
**负责人**：Agent
**规格**：[`docs/ai-workflow.md`](../docs/ai-workflow.md) §13
**依赖**：T041（skill）、T043（真实题面）
**涉及层**：服务端

## 问题

用户问：**怎么让模型更快、更省 token 地把文字变成能直接画图的代码？**
这是成本和延迟的问题，所以**先量**。

## 量

| | |
|---|---|
| 系统提示词（规则 + 规范 + 范例 + 命令表） | **5847 字符 ≈ 2900 token** |
| 用户那句话 | **35 字符** |
| 一次重试 | 再发一遍系统提示词（前 3 次失败就是 **~8800 token**） |
| 命令表 | 1427 字符（63 条，每条约 23 字符 —— 已经很紧） |

**结论：成本几乎全在提示词上，而提示词是*固定的***。
所以真正的杠杆不是"把提示词写短"，是**别再重复付它的钱**：

1. **前缀缓存**（provider 侧）。系统提示词跨请求完全一致，而且**稳定**
   （无时间戳、无随机、无 `current` 图混入 —— 当前图在 user 消息里）。
   DeepSeek / OpenAI 都自动做前缀缓存，命中后这部分接近免费。
2. **`max_tokens`**（已做）。请求原来**没有输出上限** —— 模型可以"想一想"写一千个 token，
   老师就等一千个 token、也付一千个 token。现在 700（一张图的代码几十行）。
3. **重试**。每次重试都要重发整个提示词；**让第一次就答对**才是省钱的唯一办法 ——
   这正是 T041 的 skill 在做的事（错误信息可照改、范例可选）。

## 第一批优化（已完成）

- `OpenAICompatibleProvider.max_tokens = 700`，写进请求体。
- 前缀稳定性确认：系统提示词不随请求变化（只有 user 消息变）。

## 下一步（按性价比）

| # | 做什么 | 省多少 |
|---|---|---|
| 1 | **流式输出**（SSE）：面板一开始就显示，感知延迟从"等 1.5 s"变成"立刻" | 不省 token，省体感 |
| 2 | **规范瘦身**：2500 字符的散文 → 表格，目标 ~1200 | ~20% 提示词 |
| 3 | **命令表按需**：只给和这次请求相关的命令（先做一个关键词筛，附一句"需要别的可以说"） | ~15% |
| 4 | **MCP 侧**：给 agent 的工具响应加 `--compact`（只回 id 和 `ok`），现在每个 `geo_construct` 都回全量节点 | 取决于图 |
| 5 | **一次调用出多个候选**（n=2），取第一个通过自检的 —— 比"失败再重试"省一轮 | 视情况 |

**不做**：把提示词砍到很小。规范里的"做不到的事"和范例是*实测*最有效的部分
（T043：换掉那张坐标表之后 21 → 22/22），为了省 token 砍掉它，省下的是钱，丢掉的是正确率。

## 已知限制

- 没有测**真实**的 token 用量（那要 provider 的用量接口）；这里量的是字符数。
- 前缀缓存是否命中由 provider 决定，本地只能保证"前缀稳定"。
- 只测了 DeepSeek 一个服务。
